# 本地搜索：走查 + 正则 vs SQLite FTS5（r34-D9）

日期：2026-10-30。环境：Windows 10/11，Node `22.19.0`，`node:sqlite`（当时仍标记为
experimental，需 `--experimental-sqlite`），FTS5 的 `trigram` tokenizer。语料与数据库
都放在 `.pack/`（gitignored），脚本：[`scripts/fts5-bench.mjs`](../../scripts/fts5-bench.mjs)。

## 1. 测什么

应用里“在所有项目中搜索”是一个**一次性、用户触发**的行级检索：每个仓库走文件树，
逐行做字面量/正则匹配。FTS5 是相反的形态：先建持久索引，查询快，但索引要维护。
本实验用同一语料比较两者，并测增量写入的成本。

语料：1 000 个文件、3 856 890 B（约 3.86 MB），每文件 60 行、200 个词表按
确定性伪随机分布，另加唯一 token；20 个字面量查询。FTS5 使用
`fts5(path UNINDEXED, body, tokenize='trigram')`，以便做子串匹配而不是整词匹配。

## 2. 实测

| 指标 | 结果 |
|---|---:|
| 走查 + 字面量（每查询，20 次的中位） | **181.3 ms** |
| FTS5 查询（每查询，10 次的中位） | **4.75 ms** |
| FTS5 首次建索引（1 000 文件） | **5 502 ms** |
| 增量写 10 个文件 | **469 ms** |
| 删除 1 行 | **322 ms** |
| 数据库文件 | 11 067 392 B |
| WAL 文件 | 11 152 872 B |
| 语料原始大小 | 3 856 890 B |

命中数不可直接比较：走查按**行**计数（140 157），FTS5 按**文件**计数（181 440）；
脚本输出里明确写了这一点，不把两个数字放在同一列下比较。

复现：

```powershell
node --experimental-sqlite scripts/fts5-bench.mjs --files 1000 --queries 20
```

## 3. 结论：暂不接入（no-go）

FTS5 查询快 38×，但代价在别处：

- **首次索引 5.5 s**，而应用当前的一次完整搜索在 100 ms 量级；索引必须建在用户提出
  问题之前，启动、克隆、git 切换、编辑器保存都会让索引失效。
- **增量写 10 个文件 469 ms，删除 1 行 322 ms**（D: 的 fsync 慢是放大因素，但即使
  快盘也不为零）。应用管理的是“正在开发”的仓库，文件每天变化；维护成本会落在每次
  仓库变更上。
- **磁盘 22 MB（DB + WAL）对应 3.9 MB 语料**（约 5.7×），且需要 rusqlite/自带 SQLite
  的依赖与许可证评估；当前零依赖的 `regex + walkdir` 已经满足单次搜索。
- **语义不同**：FTS5 trigram 支持子串，但排序（BM25）与应用的“按仓库分组、要文件行”
  并不是同一种结果；接入还要重写结果层。

因此 r34 选择**继续用走查 + 正则**，并补上取消与进度（D4）。什么时候重新评估：
搜索变成高频重复查询、语料静态（例如只索引 README）、或者单次走查在真实集合上超过
1 s。到那时 FTS5 的查询优势才可能盖过维护成本。

## 4. 边界与未验证

- 语料是合成的；真实源码的目录结构、文件大小分布与改动频率不同。
- Node `node:sqlite` 是实验特性；Rust 侧接入需要 `rusqlite` 或类似依赖，本次没有做
  供应链/许可证评估（只作为未来的门）。
- 没有测并发查询、内存峰值、WAL checkpoint 行为；也没有测 Windows 上多处
  `git clone` 同时写索引的争用。
- 走查基线是 Node 读取 + `includes`，不是 Rust `regex` 的精确实现；两者在同一数量级，
  但不能把 181.3 ms 当作应用后端的确切数字。
