# 200 个仓库的健康扫描（r35，2026-10-31）

日期：2026-10-31。对象：`health::repo_health_overview` 的 4 路并行实现（`map_parallel`），
在 0.4.0 便携布局的 release 二进制上，通过 WebView2 CDP 调用 IPC 测量。

## 1. 夹具

```powershell
node scripts/scale-fixture.mjs --root .pack/scale-health --count 200
# 再把一份 `git init` 出来的空 .git 复制进每个仓库，保证 git status 可解析
```

夹具是 200 个 `<root>/<owner>/<repo>/.git` + `.devhub.json`，每个仓库都是有效的空
Git 仓库（`branch.head=master`，`.devhub.json` 是唯一未跟踪文件）。不是真实用户集合，
也不覆盖网络盘/巨型仓库。

## 2. 方法

- 把 release `devhub-app.exe` 放到独立目录（便携布局），写一份只含
  `projectRoot=<checkout>/.pack/scale-health` 的 `devhub-config.json`。
- 用 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` 启动，
  CDP 连续调用 `repo_health_overview` 三次。
- 记录 Rust 返回的 `elapsedMs`，同时记录墙钟；两者在测量中相差 <30 ms。

## 3. 结果

| 运行 | 墙钟 | Rust elapsedMs | scanned | rows | capped | git 错误 |
|---|---:|---:|---:|---:|---|---:|
| 1 | 6301 ms | 6276 ms | 200 | 200 | false | 0 |
| 2 | 6090 ms | 6068 ms | 200 | 200 | false | 0 |
| 3 | 5700 ms | 5677 ms | 200 | 200 | false | 0 |

前三条分支均为 `repo_health_overview.rows` 的 `master`，`hasGit=true`。扫描上限
`MAX_HEALTH_REPOS=200` 正好覆盖夹具，`capped=false`。

## 4. 结论与边界

- 200 个仓库的 `git status --porcelain=v2 --branch` 在 4 路并行下约 **5.7–6.3 s**
  （本机 D: 慢盘），行序与墙一致（`map_parallel` 的输入序合并）。
- 这是**空仓库**的读数；真实仓库的 `git status` 工作量更大，不能直接外推。
- `repo_health_overview` 没有取消/进度事件，200 仓库上限之外的部分只由 `capped` 标记；
  这是已知缺口，不是本实验的结论。
- 串行基线没有在本轮重测；r35-G3 的合成 40×10 ms 对照是 416 ms → 104 ms，只证明
  并行映射的调度收益。
