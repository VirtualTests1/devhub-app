# 英文词典按需加载（r32-O1）

日期：2026-10-29。对象：`src/lib/i18n.ts`（zh 词表 + 查找 + 懒加载器）与
`src/lib/i18n-en.ts`（英文值数组）。

## 1. 为什么动

英文词表是入口包中最大的一块“大多数启动不需要”的 JS：默认语言是 zh-CN，且 zh-CN
同时是回落表；英文只在用户主动切到 `en` 时才有内容价值。r31 结束时初始 JS 预算
748,454 B，实测 747,430 B（99.9%），每加一条界面文案都要重钉预算。

## 2. 做法

- `EN_VALUES` 搬到 `src/lib/i18n-en.ts`，保持“按 ZH 键序的值数组”契约，不重新引入键名；
- `i18n.ts` 用 `import("./i18n-en")` 动态加载，Vite 产出独立 `i18n-en-*.js`；
- `DICTIONARIES.en` 初始为空对象；`installEnglish(values)` 按 `ZH` 键序填充并通知订阅者；
- `ensureEnglish()` 只加载一次，失败时不伪装成功；未加载期间任何 `en` 查询经
  `resolveKey` 回落到 zh-CN，不出现空白或键名；
- 启动时若存了 `en`，模块末尾预热该 chunk，不阻塞首帧；
- 切到 `en` 时立即切换 locale 并发起加载，chunk 到达后 `installEnglish` 触发重绘
  （中途界面显示中文，属于明确的回落，不是“假装英文已加载”）；
- 测试进程（`tests/helpers/register.mjs`）在启动时静态导入并安装英文，保证断言看到
  真实词表；一个子进程测试使用 `DEVHUB_TEST_SKIP_ENGLISH=1` 验证“全新进程先回落、
  再按需加载”的真实路径。测试的静态导入不进入应用产物。

## 3. 实测（同一构建命令 `pnpm build`）

| 指标 | r31 | r32 | 变化 |
|---|---:|---:|---:|
| 初始 JS（entry + modulepreload） | 747,430 B | **682,319 B** | −65,111 B（−8.7%） |
| JS 总量 | 1,145,471 B | 1,158,729 B | +12,234 B |
| 最大单块 | 257,827 B（ui-shared） | 206,852 B（vendor-react-dom） | −50,975 B |
| JS+CSS 总量 | 1,225,253 B | 1,238,909 B | +12,632 B |

总量上升来自本轮四个新界面（队列优先/历史、Markdown 清单、提交历史），不是英文词表
回潮；`i18n-en-*.js` 为 76.5 KB，只有选择英文时才下载。预算常量已按实测重钉，
`node scripts/check-dist.mjs` 通过。

## 4. 边界与未验证

- 没有在真实 WebView2 窗口中测“切到英文到重绘完成”的实际延迟；只验证了构建分块、
  加载器状态与回落规则。
- 英文加载失败时界面保持中文并打印一次 console.warn；没有做“重试按钮”。
- 词表仍只覆盖已接线的界面。README 已改为“部分界面支持英文（尚未全量翻译）”，
  与事实一致；本轮之后日期/时长格式化与原生确认框也接入了语言切换，但仍有
  Rust 侧生成的句子（如部分操作结果）保持中文。
