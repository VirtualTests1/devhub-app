# 1 000 个仓库的墙扫描与 slug 解析（r34-D8）

日期：2026-10-30。二进制：`pnpm tauri build --debug --no-bundle` 产物
`src-tauri/target/debug/devhub-app.exe`（打包 dist，不是 dev build）。夹具：
[`scripts/scale-fixture.mjs`](../../scripts/scale-fixture.mjs) 生成的 1 000 个
`<root>/<owner>/<repo>/.git` + `.devhub.json`，位于 `.pack/scale-1000/`（gitignored）。

## 1. 为什么要改 `--scan-check`

r33 的 `--scan-check` 对**每个 slug** 调用一次 `find_repo_by_slug`，而后者每次都重走
整个容器，因此是 O(n²)。50 个仓库时是 1.6 s；1 000 个仓库时超过 10 分钟没有结束，
只能中止。r34 把“解析 slug”阶段限制为固定样本（`SCAN_LOOKUP_CAP = 20`），并显式打印
`sampled=20/1000`；索引侧用同一组样本比较，因此仍然是一次可对照的前后读数。

## 2. 实测

```powershell
node scripts/scale-fixture.mjs --root .pack/scale-1000 --count 1000
src-tauri\target\debug\devhub-app.exe --scan-check 2 `
  D:\wai\Project\DeepSeekHarness\issues\devhub-app\.pack\scale-1000
```

| 阶段 | 读数 |
|---|---:|
| walk（冷，第一次运行） | 10 161 ms |
| walk（热） | 813 ms |
| list（walk + identity） | 784 / 826 ms |
| 20 次 legacy slug 解析（每次全走） | **16 721 / 16 952 ms** |
| 索引冷读（磁盘 `.devhub-index.json`） | 228 ms |
| 20 次索引 slug 解析 | **47 ms**（约 2.35 ms/次） |
| 同一索引再次读取 | 3 ms（memory） |
| 失效后重校验一次 | 174 ms |
| 目录访问 / marker 读取 | 41 个目录 / 1 000 次 |

冷 walk 的 10.2 s 只在构建后第一次运行出现；第二次同命令是 813 ms。没有把它当成代码
回归，也没有为了这个数字改代码——它更像是构建/杀毒扫描后的冷缓存。索引冷读 228 ms 与
r33 的 50 仓 85 ms 同量级；每 slug 从约 845 ms（legacy）降到约 2.35 ms（索引）。

## 3. 结论

- `list_repositories` 在 1 000 个仓库上仍低于 `--scan-check` 的 1.5 s 预算（约 0.8 s）；
  项目墙的 48 张窗口化渲染继续负责 DOM 侧的上限。
- 索引的价值随规模变大：50 仓时约 316×，1 000 仓时约 360×（按每次 slug 解析）。
- `--scan-check` 现在在 1 000 仓规模可用（约 17 s/轮），但它是**采样**诊断，不是
  “全部 slug 的完整成本”。完整成本仍是 O(n²)，生产路径不这么用。
